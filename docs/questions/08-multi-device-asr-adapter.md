# 第 8 题：多机型多 ASR 厂商如何分层

核心矛盾在于：每来一款新主板，音频编码不同、唤醒上报方式不同、控制指令格式不同；每换一家 ASR，接口又不一样。如果每来一个就在主流程里加分支，代码很快会失控。

## 模块划分

设备接入层负责连接、鉴权和按 deviceId 路由。

协议适配层把各家不同的上行格式统一成内部事件。

ASR 适配层对接各家 ASR，统一成开始、推帧、结束、取消四个动作。

对话服务只处理统一事件进、统一指令出，不关心对面是什么机型。

指令适配层把统一指令翻译成对应机型的格式。

最上层是一张配置表，记录哪个机型使用哪个协议、哪个厂商、支持哪些能力。

## 使用的设计模式

### 适配器

这是主要模式。协议适配和 ASR 适配都是适配器，把外部各不相同的格式转成内部统一的形式，主流程只依赖统一接口。

### 工厂加注册表

解决"新机型去哪里找实现"的问题。启动时读取配置，建立"机型到适配器实例"的映射。运行时按 deviceId 查表，不写大量条件判断。

配置形式：

```yaml
devices:
  board_x:
    protocol: x_protocol
    asr_provider: vendor_y
    capabilities: [aec, wake_word, tts_stream]
```

### 策略

同一能力存在多种实现时使用。例如端点检测，可以由设备判断、云端计算能量、或参考 ASR 中间结果，三种方式可以按机型配置。

### 模板方法

ASR 的生命周期是固定的：打开、推帧、结束或取消、关闭。各家厂商内部实现不同，但流程一致。因此用基类固定流程，子类实现细节。

## 统一模型

### 上行音频事件

```json
{
  "event": "audio",
  "device_id": "d-1",
  "turn_id": "d-1:12:3",
  "seq": 42,
  "timestamp_ms": 1320,
  "codec": "opus",
  "sample_rate": 16000,
  "channels": 1,
  "is_last": false,
  "payload": "base64..."
}
```

各家的映射方式：

主板 A 使用 JSON 加 base64，字段直接映射。

主板 B 发送二进制帧头加 PCM，先解析帧头取出 seq 和时间戳，再把 PCM 转成 opus 填入。

主板 C 使用 TLV，按 tag 号对应到统一字段。

### 下行设备指令

```json
{
  "command": "speak",
  "device_id": "d-1",
  "turn_id": "d-1:12:3",
  "text": "北京今天晴，12 到 24 度",
  "audio_url": null,
  "interruptible": true
}
```

指令类型包括：说话、停止、开始监听、灯效、报错。

主板 A 接收 JSON。主板 B 接收固定字节码。主板 C 接收 XML。指令适配层负责转换。

## 新增"机型 X + 厂商 Y"的改动范围

### 必须修改的

编写机型 X 的上行解析和下行编码。

编写厂商 Y 的 ASR 适配器，实现打开、推帧、结束、取消四个方法。

配置表增加一行。

补充测试。

### 理论上不需要修改的

对话服务不需要改动。

设备接入层只要协议仍是 WebSocket 或 HTTP，也不需要改动。

端点检测和状态机不需要改动。

其他机型和厂商的实现不需要改动。

对话服务接口和 Agent 不需要改动。

改动集中在适配器层，业务代码保持不变，这是分层的价值所在。

## 测试方式

协议适配器用契约测试。所有适配器接收同一组输入，输出的统一事件必须一致。可以用属性测试，也可以用固定样例。

每个适配器单独测试，使用真实录制的二进制样本，断言 seq、时间戳、音频数据都正确。

ASR 适配器同样用契约测试。同一段音频交给各厂商实现，都要能产出非空的最终文本，取消操作也能正常完成。

启动时校验配置。每个机型的 protocol 和 asr_provider 都必须能找到实现，找不到直接启动失败。

端到端测试一条：模拟设备 X 走完整流程，建连、推流、端点、对话、下发。

真实厂商接口不在单元测试中调用，用录制回放代替，省钱也稳定。

## 小结

用适配器隔离协议差异，用注册表隔离配置差异，用策略隔离实现差异。

主流程只认统一的上行事件和下行指令。新增机型或厂商时，只增加适配器和配置，业务代码不需要改动。
