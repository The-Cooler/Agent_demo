# 第 3 题：首 token 要 2 秒，工具又很慢，怎么处理

硬件对话场景要求首 token 在两秒内返回，但工具调用通常需要几百毫秒到几秒。这两个要求直接冲突。

解决思路是：用户听到的第一句话不需要是最终答案。

## 首 token 的实际含义

用户感知的慢，指的是说完话之后没有反应。需要的不是答案，而是"我收到了，正在处理"这个信号。

所以接入层先立即返回确认。

设备把语音发上来后，云端在两百毫秒内返回：

```json
{"type": "ack", "turn_id": "xxx", "state": "thinking"}
```

此时还没有发起任何模型调用。但设备可以点亮指示灯、播放提示音、提前打开 TTS 通道。用户体验从"没有反应"变成"正在处理"。

## 流式输出

模型调用使用流式接口，不等整段生成完成，第一个 token 出来就转发，设备侧可以立即开始播报。

对硬件场景来说，第一段内容最好是短句，例如"稍等，我查一下"。这样 TTS 立刻有话可说，后面的推理和工具调用都在这个空隙中完成。

第一段输出得快不快，取决于排队时间和 prefill。prefill 就是模型读取上下文的过程，上下文越长越慢。第 2 题的 KV cache 优化作用就在这里。

## 工具走并行的路径

关键点是不能把工具放在关键路径上同步等待。

思路是：

```
需要调用工具时：
  先异步发起工具调用
  同时生成不依赖工具结果的引导语
  工具返回后，把结果加入上下文，继续生成
  工具超时，用兜底话术继续
```

几个细节：

工具之间没有依赖时并行执行，总耗时取最慢的那个，而不是求和。这一步经常被忽略，实际能省不少时间。

每个工具单独设置超时。超时后给它一个明确的失败结果，由 Agent 决定怎么向用户解释。

慢工具可以延后到下一轮。例如用户问"明天天气怎么样，顺便订个闹钟"，天气查询慢，就先回答天气，闹钟放到下一轮。

## 传输层

设备端使用 WebSocket，服务端推送增量事件，包括状态变化、token、工具开始、工具结束、最终结果。

每个事件带 turn_id 和一个递增序号。设备收到序号回退的事件直接丢弃，重复的也丢弃。

断线重连时，设备上报最后收到的序号，服务端从该位置继续推送。这一点对硬件场景很重要，WiFi 不稳定时缺少这个机制体验会明显下降。

## 打断处理

用户正在听播报时再次唤醒，需要立即停止当前生成和播报，进入新一轮。

这要求生成任务本身可取消，工具调用也不能无限期挂起。取消和超时两个机制都需要有。

## 容易出问题的地方

不能编造工具结果。可以说"正在查询"，但查询完成前不能描述查到的内容。

每个异步分支都要有出口：要么有结果，要么有超时，不能出现一直等待的情况。

并行工具的返回顺序不固定，回填上下文时按调用 ID 对齐，不能按到达顺序排列。

重连可能导致同一轮被触发两次，需要靠 turn_id 去重。

用户打断后，未完成的工具调用应该取消，避免继续消耗配额。

度量口径也需要区分：首 token 指标要区分"ack 事件"和"第一段可播报文本"，混在一起计算会失真。

## 时间预算

ASR 最终结果 0.3 到 0.8 秒。
接入层 ack 两百毫秒以内。
上下文组装五十毫秒，从内存或 Redis 读取。
模型 prefill，缓存命中时 0.2 到 0.5 秒。
首 token 与 prefill 基本同时输出。

合计约 0.7 到 1.5 秒，能压进两秒。

工具调用不在这条链路上，它在第一段反馈之后并行进行。

## 小结

两秒首 token 的实现方式是：接入层立即确认，模型流式输出引导语，工具在旁路异步执行。超时和打断都有明确处理，不能有环节阻塞整轮。
