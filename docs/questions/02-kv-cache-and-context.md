# 第 2 题：KV cache 和 context 怎么配合

先说结论：KV cache 的命中条件只有一个，就是前缀完全一致。所以 context 怎么组装、按什么顺序组装，直接决定缓存能不能命中。

## 为什么只认前缀

模型生成时，每个 token 的 K/V 向量只依赖它之前的内容。如果前缀没有变化，这部分向量可以直接复用，不需要重新计算。

但只要前缀里改动一个字符，从那之后的所有缓存都会失效，需要整体重算。

所以 system prompt 里放当前时间、用户名、待办列表这类每轮都变的内容，看起来只是增加了几十个 token，实际会让整个缓存失效。

## 以这个项目为例

当前 demo 的上下文结构是：

```
[system]  角色 + 工具定义 + 协议 + 待办快照 + 会话摘要
[history] 最近 N 条消息
[current] 当前输入
```

按 KV cache 的标准看，这里有三处问题：

一是待办快照放在 system 里。待办每轮可能变化，一变，system 之后的全部缓存失效。

二是会话摘要也在 system 里，而且放在末尾。触发压缩时摘要变化，前缀同样中断。

三是历史消息取最近 N 条，这是一个滑动窗口，每轮窗口都向前移动，前缀每轮都在变。

这种拼法实际上等于每轮都从头计算，缓存基本用不上。

## 调整后的顺序

原则是变化慢的放前面，变化快的放后面：

```
[固定]   角色 + 工具定义 + 协议        ← 几乎不变，可跨会话复用
[会话级] 会话摘要                     ← 只有压缩时变化
[历史]   历史消息                     ← 只追加，压缩时重构一次
[尾部]   待办快照 + 当前输入          ← 每轮变化，放最后
```

这样固定部分始终命中，摘要在两次压缩之间保持命中，历史只往后增长，前面部分可以复用。只有尾部几十个 token 需要重算。

## 具体做法

工具定义的顺序固定。不同语言字典顺序可能不同，最好按名称排序后再序列化。

system prompt 加版本号。版本不变就保证字节级一致；修改 prompt 时升版本，让缓存自然失效。

历史消息不用最近 N 条的滑动窗口，改成从上次压缩点往后全部保留。超出阈值时压缩一次，压缩后产生新的稳定前缀，之后继续追加。两次压缩之间命中率是单调上升的。

多实例部署时，同一会话尽量路由到同一推理节点，否则每个节点各维护一份缓存，复用率会被分散。网关按 session_id 做一致性哈希即可。

压缩频率也不要太高。压缩本身是一次模型调用，而且会让缓存失效，设置在窗口的 75% 到 85% 之间比较合适。

## 收益

假设固定前缀两千 token。这部分如果每轮重算，按常见推理速度大约需要零点几秒到一秒。命中缓存后这部分时间完全省掉。

第 3 题中两秒首 token 的目标，很大一部分依赖这个优化。

## 小结

KV cache 不是独立的优化点，而是对 context 组装方式的硬约束。

把 context 当成只能往后追加的日志，而不是每轮重新拼接的字符串，缓存命中率自然就上去了。
