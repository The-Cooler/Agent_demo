# 第 5 题：Agent 和后端各存一份数据，如何保持一致

传统架构里数据只有一个位置，后端管理。Agent 介入之后必然要保存自己的状态，两份数据很容易对不上。

最危险的后果不是显示错误，而是模型基于过期数据做决策。比如库存已经售罄，Agent 的上下文里仍记录有货，它就会去下单。这比普通的缓存不一致严重得多。

## 先划定职责

我的做法是先区分数据归属：

订单、库存、余额由后端负责。Agent 侧最多存一个影子副本，用于提示，不能当作事实。

用户偏好、地址同样由后端负责。

对话历史、待办由 Agent 管理，后端不参与。

摘要、向量记忆是 Agent 自己计算出的派生数据，丢失后可以重建。

工具调用结果不算数据，只在当前这一轮有效，下一轮不应作为事实使用。

界线是：凡是会影响外部世界的，以业务后端为准。Agent 侧的副本只能用于检索和提示，替代不了实时查询。

## 具体做法

写入全部走后端接口。Agent 不直接连数据库，所有写操作都通过工具接口，后端负责校验、事务和审计。这样 Agent 的写操作就变成一次普通 API 调用，可以复用第 4 题的幂等设计。

Agent 记住的内容，要么存引用，要么存快照，并且带版本号。

```json
{"order_id": "A123", "status": "shipped", "version": 7, "cached_at": "..."}
```

仅用于展示时，拿快照没有问题。凡是要根据数据再做判断的，必须重新拉取最新版本。后端返回版本号，Agent 写回时带上，后端做乐观锁校验，版本不一致就拒绝。

后端数据变化后主动通知。订单状态变化、库存变动时发出事件，Agent 侧订阅并清除相关缓存。没有事件系统时，缓存时间要设得短，关键判断前强制查询。

还有一个容易忽略的点：对话状态不等于业务状态。用户上一轮说过"我买了个耳机"，Agent 记住了，但这不代表订单真实存在。用户问"我订单到哪了"，必须去查，不能靠记忆回答。这条需要写进 prompt，同时在工具层面保证没有工具结果就不能生成答案。

最后是补偿。假如 Agent 侧已经把待办标记为完成，后端写入失败，这时候要么回滚本地状态，要么打上"待同步"标记。要避免出现"Agent 认为成功、后端实际失败"这种静默分裂。

## 一致性要求不同，处理方式也不同

余额、库存、支付需要强一致。写操作走后端事务，Agent 不缓存写结果。

订单状态这类展示内容，读己之写即可，短暂不一致可以接受。

商品描述、知识库这类内容，最终一致就够，缓存加事件失效。

对话记忆本身属于会话内数据，天然隔离。

## 小结

Agent 的记忆应当定位为派生视图，而不是第二个数据库。

写操作强制走后端，读可以缓存，但做决策前必须重新确认。用版本号或事件把不一致的时间窗口压缩到可接受范围。
