# 第 9 题：端点检测与一轮对话的状态管理

题目给出的规则是：收到有效语音帧视为说话中，连续静音达到 silenceMs 认为一句话结束，从开始算起超过 maxUtteranceMs 强制结束。结束后把文本送对话服务，拿到播报指令再下发给设备。

## 状态定义

```
空闲 ──唤醒或首帧──▶ 监听
监听 ──静音达标──▶ 收尾
监听 ──超过最大时长──▶ 收尾
监听 ──设备标记最后一帧──▶ 收尾
收尾 ──拿到 ASR 最终文本──▶ 等待对话
等待对话 ──拿到播报内容──▶ 播报中
播报中 ──播报完成──▶ 空闲 或 重新监听
任意状态 ──设备断线──▶ 挂起
任意状态 ──用户打断──▶ 打断 ──▶ 监听
```

各状态的职责：

空闲状态，未唤醒，收到的音频直接丢弃。

监听状态，正在收集当前这一句。

收尾状态，已判定结束，等待 ASR 输出最终文本。此阶段到达的音频丢弃。

等待对话状态，文本已提交对话服务，等待返回。

播报中状态，正在播报，默认不监听。

挂起状态，连接断开，状态保留，等待重连。

## 静音判定

每一帧计算一个语音标记：

```
有语音 = 当前帧能量超过阈值
       或 ASR 中间结果标记存在文字
```

连续超过设定时长没有语音，触发端点。

一个容易写错的地方：静音计时从最后一帧有语音的位置开始算，不是从第一帧静音开始算。否则会截掉句尾。

## 静音的来源

三种来源各有优劣：

设备端判定。省带宽，设备本地完成。但机型之间差异大，阈值难以统一。

云端计算能量。策略统一，不依赖机型。但环境嘈杂时误判率高。

参考 ASR 中间结果。最接近语义。但依赖厂商，且有延迟。

实际方案是组合使用：设备端判定作为提示，云端用能量和 ASR 中间结果做最终判断。三者中有两个认为结束时，进入收尾。

## 强制结束

从收到第一帧开始计时，超过 maxUtteranceMs 后不再等待静音，直接进入收尾。

这会截断长句，因此需要在日志和播报结果中标记截断，便于后续调整参数。

## 播报结束后的两种策略

题目专门问了这两种策略，差异比较明显。

### 策略一：播报结束后自动监听

播报结束立即进入监听状态，用户不需要再次唤醒。

优点是交互流畅，适合连续对话场景。

缺点是容易误收。设备扬声器的声音会被麦克风拾取造成自激，必须有回声消除。周围环境音也可能被识别为说话。用户不说话时会产生空轮次。

缓解方式：播报结束后先忽略三百毫秒左右再开始监听；同时要求第一段语音达到最小时长，过短的丢弃。

### 策略二：播报结束后回到空闲，等待下次唤醒

优点是不会误收，安全，适合一句话指令型的硬件。

缺点是每次都需要唤醒，操作成本更高。

### 选择依据

取决于两件事：设备是否具备回声消除能力，场景是否需要连续对话。

这两点在配置里按机型区分，对应第 8 题的能力表。

## 超时处理

监听阶段一直没有语音，超过最大时长后结束。ASR 返回空文本时不提交对话服务，直接回到空闲。

收尾阶段等不到 ASR 最终结果，超时后使用最后一次中间结果，实在没有则返回错误提示。

等待对话阶段对话服务超时，播报"网络异常"提示，回到空闲。

播报阶段被中断，立即发送停止指令，然后进入监听或空闲。

## 小结

用状态机管理一轮对话。端点由静音时长和最大时长两个条件共同决定，静音判断结合设备、能量和 ASR 中间结果三种来源。

播报结束后自动监听还是等待唤醒，取决于设备是否具备回声消除能力，以及场景是否需要连续对话。
