# 第 4 题：工具重试时如何避免重复下单

问题本身可以归纳为一句话：模型输出不确定，工具还会超时，超时的时候无法知道对方是否执行。直接重试可能产生两次副作用。

目标不是绝对不执行两次，而是多次重试只产生一次效果。

## 第一步：让框架知道工具的性质

这一点不能依赖模型判断，需要在注册工具时声明。

```python
class Tool:
    name: str
    side_effect: Literal["只读", "可重复写", "不可重复"]
```

分三类：

查询天气、搜索文档这类工具，重试不会改变任何状态。

修改订单状态、更新用户偏好这类工具，重试结果相同。

下单、支付、发送短信这类工具，重试会产生副作用。

第三类的处理方式不是靠提示词约束模型，而是由框架附加幂等键，把它转成第二类。

## 第二步：幂等键的生成方

这里容易出错。直觉上会想让模型生成幂等键，但这样不可行。

模型两次生成的参数可能不同，字段顺序可能不同，重试时甚至可能改变主意修改参数。用模型输出计算幂等键，等于没有计算。

幂等键必须由框架生成，并且在第一次发起调用时就生成并持久化。

```
每一步执行时，框架生成一个 call_id
call_id 随 trace 一起落库
重试时复用同一个 call_id，不重新生成
```

另一种情况是用户连续点击两次下单。这种跨请求的场景需要用业务字段组合：用户 ID、商品、数量，加上一个请求号。同样，这个键不能由模型参与生成。

## 第三步：执行时的去重

流程大致如下：

```
SET idem:{key} "pending" NX EX 86400

如果设置成功：
    当前请求是第一个，真正调用下游
    调用完成后写入结果

如果设置失败：
    说明已有调用在执行
    读取当前值
    如果是 pending，等待一段时间后重读，或直接返回"处理中"
    如果已有结果，直接返回该结果，不再调用下游
```

如果下游本身支持幂等键，把同一个键透传下去，由下游负责最终去重。支付类网关基本都支持这个机制。下游不支持时，上面的 Redis 记录就是唯一防线。

## 第四步：超时的处理

这是最复杂的部分。超时时只知道没有收到结果，无法知道对方是否已经执行。

三种处理方式：

一是查询确认。下游提供按幂等键查询结果的接口，先查一遍，有结果直接用，没有才重试。

二是等待。pending 状态仍然存在，说明可能正在执行，隔一段时间再读一次。

三是不重试。如果下游完全无法查询，就直接告诉用户结果暂时不确定，由用户决定。这个结果不理想，但比盲目重放安全。

## 第五步：几个边界

幂等记录的过期时间要足够长，至少超过客户端可能重试的最大时间窗口，一般设置为 24 小时。

存储上 Redis 负责快路径，最终结果需要落库。Redis 不可用时从库里读回。

同一用户在同一会话中两次说"下单"，语义上是两笔订单。所以键不能只按用户和商品计算，必须包含本次调用的标识。

## 一个错误做法

我见过一种实现：让模型输出一段 JSON，重试时再让模型生成一遍，比较两段 JSON 是否相同，相同就认为属于同一次调用。

这种做法不成立。两次输出字段顺序可能不同，措辞可能不同，模型也可能自行修改参数。幂等判断必须依赖框架生成的稳定标识，不能拿模型输出当依据。

## 小结

框架根据工具的副作用声明做判断，第一次调用前生成并持久化幂等键，执行侧用 SETNX 加结果回读保证只生效一次。对于无法确认状态的下游，报"不确定"比盲目重放更安全。
