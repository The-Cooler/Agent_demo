# 第 1 题：Agent 后端的 Redis 怎么设计

以前后端的 Redis 职责比较单一：缓存热点数据、存 session、做计数和限流。数据库是最终的数据来源，Redis 丢了可以重建。

Agent 接管大部分业务逻辑之后，后端的角色变了，从"最终执行者"变成"能力提供者"。一次用户请求不再对应一次数据库读写，而是一串 LLM 调用加上多次工具调用。这中间产生的状态，Redis 需要承担一部分。

## 新增的职责

我按用途分了七类。

**一次 run 的中间状态。** 比如 Agent 已经调了两次工具，正在决定是否调第三次。这些中间结果需要跨请求、跨实例可见，放 Hash 比较合适。

**长任务的状态。** 工具调用可能要几秒，不能一直占着 HTTP 连接，需要转成后台任务，状态放 Redis，进度用 Stream 推出去。

**工具调用的幂等键。** 一个下单工具超时了，无法确定对方是否执行，重试不能重复下单。Redis 的 SETNX 适合做这个去重。

**会话并发控制。** 同一个会话不能同时跑两条 run，否则历史写入会乱序。可以用状态字段做 CAS，或者用分布式锁。

**配额计数。** token 用量按用户按天累计，超过阈值就拒绝新的 LLM 调用。计数场景 Redis 很合适。

**事件分发。** 一条生成结果可能需要推给多个网关实例，Stream 能支持多个消费方各自读取。

**语义缓存。** 相似问题直接返回已有答案，省一次模型调用，需要向量检索。

## 具体结构

会话状态我按这个结构存：

```
agent:session:{id}          Hash   状态、当前 run_id、当前步数
agent:session:{id}:scratch  List   当前 run 的步骤序列
```

Hash 的好处是可以对单个字段做原子判断。请求进来先看状态是否为空闲，不是就直接拒绝。这比加分布式锁轻量。

会话历史仍然存数据库，Redis 只放热状态。进程重启后从库里恢复，中间过程丢了可以重跑这一轮。

任务和进度用 Stream：

```
agent:job:{id}          Hash    整体状态
agent:job:{id}:events   Stream  增量事件
```

选择 Stream 而不是 Pub/Sub，主要原因是 Stream 会保留消息。客户端断线后带上最后收到的消息 ID 重连，服务端从断点继续推送。Pub/Sub 断开就丢消息，硬件场景不适合用。

幂等键的结构：

```
idem:{工具名}:{调用id}   字符串   结果，24 小时过期
```

调用工具前先 SETNX，抢到的那次真正执行，没抢到的等待后读取结果。

## 不适合放在 Redis 的数据

订单、库存、余额这类业务事实数据仍然以数据库为准，Redis 只做缓存。

长期记忆的数据量和检索需求超出 Redis 的定位，应该放向量库或专门的存储。

审计日志需要持久化和顺序保证，应该落盘。

另外，Agent 不应该绕过后端直接修改 Redis 里的业务数据，否则后续排查会非常困难。

## 小结

以前 Redis 是后端前面的缓存层，现在更像运行时的协调层：存执行中的状态、分发事件、做幂等和配额，但不承担业务事实。

边界大概是：Redis 记录"正在发生什么"，不记录"事情的结果是什么"。
